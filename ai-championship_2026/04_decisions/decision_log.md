# 의사결정 로그

## DEC-001 — File & Decision System 채택

- 날짜: 2026-09-03
- 상태: 채택
- 질문: 조사 자료와 작업 이유를 어떤 방식으로 보존할 것인가?
- 결정: `00_governance/FDS.md`의 File & Decision System을 프로젝트 기록 기준으로 사용한다.
- 이유: 결과만 남기면 후보 선택의 전제와 폐기 이유를 복원할 수 없으며, 잘못된 가정이 반복될 수 있다.
- 근거: 사용자가 모든 자료를 적합한 파일로 정리하고 작업 이유도 판단 근거로 저장하도록 요청했다.
- 고려한 대안: 하나의 긴 메모 파일에 전부 기록, 채팅 기록만 유지.
- 대안을 채택하지 않은 이유: 자료 유형과 판단 상태가 섞이고, 수치의 출처·조건을 기계적으로 추적하기 어렵다.
- 위험: 기록 자체가 개발 시간을 과도하게 사용할 수 있다.
- 완화책: 중요한 판단과 재현에 필요한 결과만 기록하고 일시적인 명령 출력은 생략한다.
- 재검토 조건: 기록 시간이 실제 구현 시간의 15%를 지속적으로 초과할 때.

## DEC-002 — Google Trends를 보조 근거로만 사용

- 날짜: 2026-09-03
- 상태: 채택
- 질문: 검색 관심도를 후보 선정 점수로 직접 사용할 것인가?
- 결정: Google Trends는 문제 후보 발굴과 사용자 의도 가설 생성에 사용하되, 시장 규모나 최종 선정의 단독 근거로 사용하지 않는다.
- 이유: 값은 절대 검색량이 아니라 비교 묶음 안에서 정규화되며 뉴스·계절성·중의어에 영향을 받는다.
- 근거: `SRC-002`~`SRC-009`, `02_research/google_trends/research_log_2026-09-03.md`
- 고려한 대안: 평균 상대지수가 높은 검색어부터 자동 순위화.
- 대안을 채택하지 않은 이유: 서로 다른 비교 묶음의 값이 비교 불가능하고 높은 관심이 AI 필요성이나 구현 가능성을 보장하지 않는다.
- 위험: 낮은 검색량이지만 중요한 B2B 문제를 놓칠 수 있다.
- 완화책: 사용자 인터뷰, 공식 통계, 도메인 문제 빈도, 지불 의사를 별도 축으로 평가한다.
- 재검토 조건: Google이 절대량 또는 일관된 교차그룹 지표를 제공할 때.

## DEC-003 — AI와 결정론적 검증의 하이브리드를 우선

- 날짜: 2026-09-03
- 상태: 아이디어 평가 기준으로 채택
- 질문: AI가 모든 판단을 담당하는 서비스를 우선할 것인가?
- 결정: AI는 비정형 입력 해석과 후보 생성에 사용하고, 법정 기준·수치·금지 조건은 규칙과 출처로 검증하는 구조를 우선한다.
- 이유: 해커톤에서는 AI 필요성을 보여주면서도 실제 사용 가능한 신뢰성을 확보해야 한다.
- 근거: `01_brief/ai_service_definition.md`
- 고려한 대안: 완전 룰베이스, 완전 자율 AI 에이전트.
- 대안을 채택하지 않은 이유: 완전 룰베이스는 AI 가치가 약하고, 완전 자율 방식은 오류를 통제하고 설명하기 어렵다.
- 위험: MVP 범위가 커질 수 있다.
- 완화책: 데모의 한 가지 핵심 흐름에만 AI와 검증 규칙을 결합한다.
- 재검토 조건: 선택된 문제에서 오류 비용이 매우 낮거나 결정론적 검증이 불가능할 때.

## DEC-004 — 도메인 중심에서 문제 기능 중심으로 조사 확대

- 날짜: 2026-09-03
- 상태: 채택
- 질문: 익숙한 산업 영역을 중심으로 후보를 더 깊게 조사할 것인가, 전 영역으로 다시 넓힐 것인가?
- 결정: 최종 후보를 좁히기 전까지 특정 산업에 가산점을 주지 않고, 감지·검증·번역·구조화·조정·개인화·시뮬레이션·기억·매칭·실행의 문제 기능과 다양한 사용자 상황을 교차해 조사한다.
- 이유: 초기 20개 후보가 주거·건설·안전·업무 영역에 상대적으로 집중됐다. 이 상태에서 깊이 조사하면 익숙한 도메인만 강화하는 확증편향이 생길 수 있다.
- 근거: 사용자의 범위 확대 요청, `02_research/problem_space/problem_archetype_map.md`
- 고려한 대안: 초기 유망 후보 6개만 바로 상세 조사.
- 대안을 채택하지 않은 이유: 대 후보 공간을 충분히 탐색했다는 근거가 없으며, 새로운 사용자군과 문제 유형을 놓칠 가능성이 높다.
- 위험: 후보 수가 많아져 조사 시간이 분산될 수 있다.
- 완화책: 문제 기능별 최소 수만 확보한 뒤 공통 평가 기준과 탈락 조건으로 압축한다.
- 재검토 조건: 사용자 상황 10종과 문제 기능 10종의 교차 탐색이 최소 1회 완료됐을 때.

## DEC-005 — IDEA-051은 개인 하루 일기로 진입하고 기록 엔진으로 확장

- 날짜: 2026-09-03
- 상태: 제품 프레이밍으로 채택, 최종 출품 선정은 미정
- 질문: 사진 기반 대화형 기록을 처음부터 여러 기록 유형으로 만들 것인가?
- 결정: 첫 사용자 경험과 해커톤 데모는 `하루치 사진 → 대화형 회고 → 개인 일기`로 제한하고, 여행·육아·가족·프로젝트 기록은 같은 엔진의 확장 가능성으로만 보여준다.
- 이유: 일기는 감성적 가치와 AI 대화를 짧게 설명할 수 있지만, 여러 기록 유형을 동시에 구현하면 핵심 사용자와 질문 설계가 흐려진다.
- 근거: `SRC-021`, `03_ideas/concepts/IDEA-051_photo_reflection_journal.md`
- 고려한 대안: 업로드 시 일기·여행기·육아기록·업무기록을 모두 선택하게 하는 범용 기록 도구.
- 대안을 채택하지 않은 이유: 일정 도구의 목적은 넓어지지만 기존 범용 AI 요약기와 구분하기 어렵고 MVP 범위가 커진다.
- 위험: 개인 일기 시장에서 Apple Journal과 Day One 같은 강한 인접 제품과 직접 비교된다.
- 완화책: 사진 묶음의 시각 타임라인, 사진 밖의 기억 인터뷰, 문장별 사진·답변 근거를 차별화의 필수 조건으로 둔다.
- 재검토 조건: 사용자 테스트에서 여행·육아처럼 동기가 강한 특정 기록 유형이 일반 하루 일기보다 현저히 높은 완료율을 보일 때.

- 완화책: 강등 후보를 삭제하지 않고, 한국 데이터나 좁은 실행 검증 가설이 확보되면 복귀시킨다.
- 재검토 조건: `IDEA-031`에 실제 목격 제보 데이터가 확보되거나 `IDEA-045`가 실제 코드 재실행 검증기로 좁혀질 때.

- 이유: RightsLedger는 대회 자체의 라이선스 준수 요구, C2PA 기반 기술 검증, 합성 정답셋을 연결할 수 있다. 사진이 묻는 하루는 경쟁이 강하지만 기억 회수·소유감·문장 근거를 동일 입력으로 측정할 수 있다. ProjectRescue는 문제 근거가 약한 대신 중단 상태-설명서 정렬의 직접 경쟁이 상대적으로 적고 범용 VLM 대체 여부를 하루 안에 판정할 수 있다. HomeDefect는 문제 근거가 가장 강하지만 homepic과 Wefect가 증거·AI·누락검토·PDF라는 결과 대부분을 이미 제공한다.
- 근거: `SRC-046`, `SRC-049`, `SRC-050`, `SRC-060`~`SRC-066`, `02_research/competitive/phase2_deep_scan_2026-09-03.md`, `03_ideas/screening/phase2_scores_2026-09-03.jsonl`
- 고려한 대안: HomeDefect를 ProjectRescue 대신 선정, 사용자 제안만 바로 개발, 점수 1위 RightsLedger 즉시 확정.
- 대안을 채택하지 않은 이유: HomeDefect는 현행 결과 중복이 크다. 사용자 제안 여부는 경쟁 우위가 아니며, 분석 점수만으로 실제 AI 정확도와 사용자 가치를 알 수 없다.
- 위험: RightsLedger의 관계 추출이 불안정할 수 있고, 사진이 묻는 하루는 Day One·Memex보다 나아지지 않을 수 있으며, ProjectRescue는 시장 문제의 절실함이 낮을 수 있다.
- 완화책: 각 후보의 통과 숫자를 실험 전에 고정하고 실패 시 점수와 무관하게 중단한다. 세 후보를 동시에 완제품으로 만들지 않는다.
- 재검토 조건: RightsLedger 누락 증거 재현율 90% 미만, IDEA-051 소유감 개선 0.5/5 미만, ProjectRescue의 범용 VLM 대비 정확도 차이 10%p 미만 중 하나가 발생할 때. 탈락 자리는 HomeDefect의 공식 절차 감사 실험으로 대체한다.

## DEC-011 — RightsLedger 관계 연결 스파이크 통과, 최종 선정 보류

- 날짜: 2026-09-04
- 상태: 구성요소 통과, 블라인드 검증 대상으로 유지, 최종 출품 선정 보류
- 질문: 첫 기술 실험 결과만으로 `IDEA-033 RightsLedger`를 최종 출품 주제로 확정할 수 있는가?
- 결정: 정확 일치보다 의미 임베딩이 관계 후보를 크게 개선한다는 구성요소 가설은 통과로 본다. 그러나 사전 등록한 전체 기준선과 사람 시간 검증이 끝나지 않았으므로 RightsLedger를 최종 출품으로 확정하지 않는다.
- 이유: 하이브리드는 관계 F1 0.990, 누락 증거 재현율 1.000, 법률 결론 0건으로 자동 기술 기준을 넘었다. 반면 비교 기준선이 범용 생성형 LLM이 아니었고, 프로젝트당 주 자산 15개·C2PA·실제 미디어 이해·사람 감사 시간을 시험하지 않았다. 좁은 성공을 전체 제품 성공으로 확대하면 잘못된 조기 확정이 된다.
- 근거: `06_experiments/rightsledger_24h/results/comparison_2026-09-04.json`, `06_experiments/rightsledger_24h/results/experiment_report_2026-09-04.md`, `06_experiments/rightsledger_24h/run_manifest_2026-09-04.json`, `WORK-021`
- 고려한 대안: 현재 수치로 즉시 출품 확정, 범용 LLM 기준선 부재를 이유로 후보 즉시 탈락, 거짓 음성 1건을 없애도록 유사도 임계값을 사후 하향.
- 대안을 채택하지 않은 이유: 즉시 확정은 미측정 항목을 무시한다. 즉시 탈락은 규칙 대비 AI 상승폭이라는 유효한 기술 신호를 버린다. 사후 임계값 조정은 현재 정답셋에 맞춘 과적합이며 사전 기준의 의미를 훼손한다.
- 위험: 데이터 작성자와 평가 설계자가 같고, 실제 미디어 대신 사전 작성 설명을 사용해 관계 F1이 과대평가됐을 수 있다. 누락 경고 정밀도 0.800은 실제 프로젝트에서 경고 피로를 만들 수 있다.
- 완화책: 현재 임계값을 동결하고 독립 작성 5개 프로젝트에서 블라인드 재시험한다. 범용 LLM 프롬프트, 검토자 배치, 시간 정의, 통과·탈락 규칙은 데이터 확보 전에 고정한다.
- 재검토 조건: 관계 F1 0.85 미만, 누락 증거 재현율 1.00 미만, 법률 결론 1건 이상이면 중단 또는 한 항목만 수정해 재실험한다. 정확도 게이트를 유지한 사람 시간 감소 중앙값이 30% 미만이면 탈락, 30~50% 미만이면 미결, 50% 이상이면 전체 24시간 게이트 통과로 본다.

## DEC-012 — 범용 LLM 기준선 확보, 블라인드 최종 판정 유지

- 날짜: 2026-09-04
- 상태: 기준선 실행 완료, 최종 출품 선정 보류 유지
- 질문: 범용 LLM 체크리스트의 예비 실패만으로 RightsLedger의 우위를 확정할 것인가?
- 결정: `qwen3:4b` 기준선 5건과 비블라인드 예비 분석은 제품 설계 근거로 사용하되, 하이브리드 우위의 정식 판정에는 사용하지 않는다. `DEC-011`의 블라인드·사람 시간 게이트를 유지한다.
- 이유: 기준선은 정답 누락 4건 중 1건만 명시적으로 찾고 존재하지 않는 경로와 위험한 제출 확신을 생성했다. 이는 AI 자유 생성보다 관계 후보와 결정론적 검증을 분리해야 한다는 신호다. 그러나 4B 단일 모델, 기존 합성 데이터, 사후 코딩이므로 전체 범용 LLM이나 실제 사용자 성능으로 일반화할 수 없다.
- 근거: `results/general_llm_preliminary_review_2026-09-04.md`, `results/general_llm_preliminary_missing_coding_2026-09-04.jsonl`, `run_manifest_general_llm_2026-09-04.json`, `WORK-022`
- 고려한 대안: 즉시 RightsLedger 최종 확정, 작은 모델이므로 결과 폐기, 결과를 보고 프롬프트를 고쳐 같은 데이터 재실행.
- 대안을 채택하지 않은 이유: 즉시 확정은 데이터·평가 독립성을 무시한다. 폐기는 실제 관찰을 버린다. 동일 데이터 재실행은 사후 튜닝으로 기준선을 불공정하게 만든다.
- 위험: 느린 사고문 생성이 기준선 사용성을 과도하게 악화시켰고, 더 큰 상용 모델에서는 누락·안전 성능이 달라질 수 있다.
- 완화책: 원시 응답과 고정 조건을 모두 공개하고, 독립 사례에서는 검토자가 최종 결과를 확정하는 정확도와 시간을 측정한다. 모델 간 우열이 아니라 `자유형 체크리스트 대 검증 가능한 장부` 흐름을 비교한다.
- 재검토 조건: 독립 블라인드 데이터에서 범용 LLM이 정확도 게이트를 만족하고 하이브리드의 사람 시간 감소가 30% 미만이면 RightsLedger를 탈락시킨다.

## DEC-013 — C2PA 상태와 권리 증거를 분리

- 날짜: 2026-09-04
- 상태: C2PA 읽기 구성요소 통과, 종단간 검증 보류
- 질문: 유효한 C2PA 매니페스트나 `untrusted` 상태를 RightsLedger의 권리 판정으로 사용할 것인가?
- 결정: C2PA에서 `manifest_presence`, `integrity_state`, `signer_trust_state`, 원시 검증 코드를 분리해 저장한다. 이 값은 파일 계보의 보조 증거로만 사용하고 라이선스·영수증·원출처 증거의 존재나 법률상 이용 허락을 대신하지 않는다.
- 이유: 공식 정상 표본은 무결성 상태가 `Valid`이면서 테스트 인증서 때문에 `signingCredential.untrusted`였고, 손상 표본은 별도로 `claimSignature.mismatch`와 `Invalid`를 반환했다. 존재·무결성·신뢰를 한 불리언으로 합치면 정상 테스트 자산을 손상으로 보거나 유효한 매니페스트를 이용 허락으로 과장할 수 있다.
- 근거: `SRC-073`~`SRC-075`, `06_experiments/rightsledger_c2pa/results/summary_2026-09-04.json`, `WORK-023`
- 고려한 대안: C2PA 제외, 매니페스트 존재를 곧 권리 확보로 처리, 모든 `untrusted`를 손상으로 처리.
- 대안을 채택하지 않은 이유: 제외하면 검증 가능한 계보 신호를 버린다. 나머지 두 방식은 기술 상태를 법률 결론으로 바꾸거나 무결성과 인증서 신뢰를 혼동한다.
- 위험: 표본이 구형 JPEG 3개뿐이라 최신 사양과 실제 카메라·생성 도구·편집 파이프라인에서 상태가 달라질 수 있다. `c2patool` 버전과 신뢰 목록 변경으로 결과가 달라질 수 있다.
- 완화책: 도구 버전, 원본·출력 해시, 원시 검증 코드를 보존한다. 독립 프로젝트에는 이번 세 표본이 아닌 C2PA 자산을 넣고 UI에 기술 상태와 권리 증거를 별도 표시한다.
- 재검토 조건: 실제 대상 포맷을 읽지 못하거나 유효·손상 상태 구분이 독립 표본에서 틀릴 때, 또는 제품 UI가 C2PA 상태를 권리 결론처럼 보이게 할 때.

## DEC-014 — RightsLedger 정식 비교는 동일 공통입력 v2만 사용

- 날짜: 2026-09-07
- 상태: 채택, 외부 실행 대기
- 질문: 기존 범용 LLM 기준선과 하이브리드 결과를 그대로 독립 검증 설계에 사용할 것인가?
- 결정: 기존 비대칭 실행은 관찰 기록으로만 보존하고 정식 우위 판단에서 제외한다. 독립 검증은 두 조건에 동일한 자산 경로·중립 설명·취득 유형을 주는 v2 계약만 사용한다. 공통 선언으로 제공되는 자산 발견은 성능 주장하지 않고 실제 미디어 추출을 별도 게이트로 둔다.
- 이유: 기존 범용 LLM은 프로젝트 파일만 받은 반면 하이브리드는 `.rightsledger_observations.json`의 설명과 취득 유형까지 받았다. 입력을 같게 한 재실행에서도 예비 누락 재현율은 0.25로 같았지만, 공정하지 않은 비교가 우연히 같은 결론을 냈다는 사실이 설계 결함을 없애지는 않는다.
- 근거: `shared_input_baseline_protocol_2026-09-04.md`, `results/general_llm_shared_preliminary_review_2026-09-07.md`, `run_manifest_general_llm_shared_2026-09-04.json`, `WORK-024`
- 고려한 대안: 기존 결과를 그대로 정식 기준선으로 사용, 기존 결과와 합성 데이터를 전부 폐기, 기존 사례에 맞춰 프롬프트나 임계값을 수정.
- 대안을 채택하지 않은 이유: 첫 방법은 입력 교란을 숨긴다. 전부 폐기하면 유효한 오류 관찰과 구성요소 신호도 잃는다. 사후 튜닝은 현재 정답에 과적합한다.
- 위험: 공통 자산 선언 자체가 실제 제품에서는 사용자 확인이나 별도 미디어 모델을 필요로 한다. 4B 로컬 모델 하나와 합성 데이터의 한계도 남는다.
- 완화책: 독립 작성자가 공통 선언을 만들고 정답은 10개 검토 완료 전까지 보유한다. 최종 관계·누락·잘못된 경로·금지 결론을 구조화해 저장하고, 실제 이미지·음원 추출은 관계 실험과 분리해 평가한다.
- 재검토 조건: 독립 데이터 작성자를 구하지 못하거나 공통 선언 작성비용이 실제 감사시간 절감보다 큰 경우, 또는 별도 미디어 추출 게이트에서 핵심 포맷을 안정적으로 설명하지 못할 때.

## DEC-015 — 독립 검증을 선행 조건에서 빼고 1인 형성평가로 MVP를 진행

- 날짜: 2026-09-07
- 상태: 채택
- 질문: 현재 프로젝트 제안자 1명만 참여 가능한 상황에서 외부 3인이 필요한 독립 검증을 기다릴 것인가?
- 결정: 기다리지 않는다. 독립 블라인드 v2는 후속 검증 계약으로 보존하고, 출품 개발은 자동 기술 평가와 제안자 1인의 형성평가를 분리해 진행한다. 1인 평가는 종단간 완료 가능성·상태 이해·마찰·안전 문제만 판정한다.
- 이유: 외부 인력을 전제로 하면 제출 일정 내 실행 가능성이 낮아진다. 제안자 한 명도 MVP의 막힘과 위험한 오해를 찾는 데는 유효하지만, 독립성·대표성·조건 간 효과를 입증할 수는 없다.
- 근거: `SRC-076`, `WORK-025`, `06_experiments/rightsledger_solo/solo_validation_protocol_2026-09-07.md`
- 고려한 대안: 외부 3인을 구할 때까지 개발 보류, 제안자의 자기평가를 정식 사용자 실험으로 보고, 사람 평가를 전부 생략.
- 대안을 채택하지 않은 이유: 보류는 대회 일정 위험이 크고, 자기평가의 승격은 편향을 숨기며, 전면 생략은 종단간 사용성 실패를 발견할 기회를 버린다.

- 질문: PHOTO-P01의 남은 평가 문항을 먼저 끝낼 것인가, 제출 가능한 서비스 수직 흐름을 만들 것인가? 키가 없는 버전을 먼저 배포할 것인가?

- 이유: 2026-09-20 제출 마감까지 한 사람이 남은 핵심 위험을 확인하려면 모든 주변 기능보다 종단간 흐름이 먼저 필요하다. 그러나 키 없이 샘플만 작동하는 사이트를 `AI 서비스 완성`으로 공개하면 실제 모델 경로와 품질을 오인하게 만든다.
- 근거: `SRC-089`~`SRC-092`, `WORK-032`, `05_deliverables/photo_reflection_mvp/BUILD_REPORT_2026-09-14.md`
- 고려한 대안: 6~10장 계약과 전체 기능을 모두 구현, Qwen3-VL 로컬 배포를 동시에 구축, 정적 샘플만 공개, 키 없이 프로덕션 링크부터 생성.
- 대안을 채택하지 않은 이유: 6~10장과 주변 기능은 비용·실패 면적을 늘린다. 로컬 모델 동시 구축은 다중 경로를 만든다. 정적 샘플만으로는 AI 서비스 정의를 충족하지 못한다. 키 없는 공개는 심사자가 첫 클릭에서 실패하는 링크를 만든다.
- 위험: 사진 수 축소로 기존 계약과 차이가 생겼고, 파일 시간은 촬영 EXIF가 아니다. 실제 Luna 질문 품질·비용·지연이 실패할 수 있으며 사이트 공개가 늦어질 수 있다.
- 완화책: 계약과 화면에 3~8장 및 파일 시간이라고 명시한다. 키 부재는 명시적 오류로 실패시키고 규칙 결과로 대체하지 않는다. 문장 근거 검사와 외부 전송 동의를 배포 전에 자동·브라우저 검증한다.
- 재검토 조건: 실제 사진에서 위험한 단정이 1건이라도 나오거나 유효 기억 질문이 0개면 프롬프트·입력 구조를 먼저 수정한다. Luna 품질이 계속 실패할 때만 다른 모델을 비교한다. 키 설정 뒤 비공개 배포가 통과하면 제출용 접근 범위를 별도 결정한다.

## DEC-022 — 앨범은 결과 확인 뒤 명시적으로 선택 저장

- 날짜: 2026-09-14
- 상태: 제안, Supabase 연결 전 사용자 확인 대기
- 질문: 사진과 기록을 자동 저장할 것인가, 사용자가 완성 결과를 본 뒤 앨범 저장을 선택하게 할 것인가?
- 결정: 기본 AI 흐름은 영구 저장 없이 유지한다. 사용자가 결과 화면에서 `앨범으로 남기기`를 선택한 경우에만 이메일 Magic Link로 계정을 확인하고, 원본이 아닌 1,280px 메타데이터 제거 사본과 기록을 private Supabase Storage·Postgres에 저장한다.
- 이유: 앨범의 재방문 가치를 만들면서도 현재의 원본 미저장 약속과 사진 최소수집 원칙을 보존할 수 있다. Magic Link는 익명 계정과 달리 브라우저 데이터 삭제나 다른 기기에서도 앨범을 다시 찾을 수 있다.
- 근거: `SRC-094`~`SRC-097`, `WORK-034`, `05_deliverables/photo_reflection_mvp/SUPABASE_ALBUM_STORAGE_PLAN_2026-09-14.md`
- 고려한 대안: 사진 선택 즉시 자동 저장, public bucket 사용, 익명 로그인만 사용, 사진 없이 일기 텍스트만 저장.
- 대안을 채택하지 않은 이유: 자동 저장은 기대와 고지 경계를 어긴다. public bucket은 URL을 아는 누구나 사진을 볼 수 있다. 익명 로그인은 복구성이 낮다. 텍스트만 저장하면 사용자가 말한 앨범 경험을 제공하지 못한다.
- 위험: 저장 버튼에서 이메일 인증이 추가되어 이탈할 수 있고, Storage 객체 삭제와 DB 삭제 중 하나만 실패할 수 있다.
- 완화책: 결과 생성까지는 로그인 없이 제공한다. private bucket·사용자별 RLS·짧은 signed URL·명시적 전체 삭제를 사용하고 부분 삭제 실패는 재시도 대상으로 기록한다.
- 재검토 조건: 사용자가 계정 없는 기기 한정 앨범을 우선하거나 Magic Link 마찰이 핵심 흐름을 막는다고 확인하면 익명 로그인을 체험용으로 비교한다.

## DEC-023 — 공개 데모와 실제 AI 활성화를 분리해 Vercel에 배포

- 날짜: 2026-09-14
- 상태: 채택, `DEC-021`의 키 전 공개 배포 보류만 부분 대체
- 질문: 서버 키가 없더라도 명시적 샘플만 작동하는 공개 링크를 먼저 제공할 것인가, 모든 공개 배포를 계속 보류할 것인가?
- 결정: 사용자의 배포 지시에 따라 공개 Vercel 링크를 제공한다. 합성 사진과 고정 결과에는 `실제 사진 분석 결과가 아님` 표시를 유지한다. 개인 사진의 실제 AI 분석은 `OPENAI_API_KEY` 설정과 실사진 품질 게이트 전까지 완성으로 주장하지 않는다.
- 이유: 공개 링크는 심사 제출 흐름과 화면 검토에 즉시 필요하지만, 샘플 성공과 생성형 AI 성공은 별개다. 두 상태를 화면과 기록에서 분리하면 공개 검토 가능성과 사실성을 함께 유지할 수 있다.
- 근거: `SRC-100`, `WORK-037`, Vercel 공개 URL과 환경변수 목록.
- 고려한 대안: 키가 준비될 때까지 URL 비공개 유지, Vinext 정적 출력만 Vercel에 제공, Sites용 빌드를 Vercel용으로 전면 교체.
- 대안을 채택하지 않은 이유: URL 보류는 사용자의 명시적 배포 지시와 제출 준비를 늦춘다. Vinext 정적 출력은 `/`와 API 함수가 없어 404였다. 전면 교체는 이미 작동하는 Sites 경로를 불필요하게 깨뜨린다.
- 위험: 공개 링크만 본 사람이 AI 기능까지 작동한다고 오해하거나, 개인 사진을 선택한 뒤 키 부재 오류를 경험할 수 있다.
- 완화책: 샘플 고지를 유지하고 공개 배포 상태를 `데모·AI 활성화 대기`로 문서화한다. 키는 저장소나 대화에 노출하지 않고 Vercel Secret으로만 설정한다.
- 재검토 조건: Vercel 키 설정 후 실제 사진 3~8장으로 관찰·질문·기록이 모두 성공하면 공개 링크를 `작동하는 AI 서비스`로 승격한다. 실사진 품질 게이트가 실패하면 공개 샘플 상태를 유지하고 입력·프롬프트부터 수정한다.
